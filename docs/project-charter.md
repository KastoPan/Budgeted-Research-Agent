# Budgeted Research Agent：项目章程与 V1 定义

> 状态：Draft v0.2  
> 用途：冻结项目目标和 V1 边界，为后续架构设计、实现与评测提供统一依据。

## 1. 项目定位

Budgeted Research Agent 是一个面向技术调研任务的成本感知深度研究 Agent。

用户输入一个复杂研究问题和有限研究预算，系统自主拆解问题、搜索并阅读公开网页、组织证据，并根据当前证据状态和剩余预算动态决定下一步研究行动，最终生成一份带可验证引用的结构化研究报告。

本项目的首要用途是作为求职简历项目，目标岗位包括大模型应用算法、Agent 开发和 LLM 应用工程。因此，项目优先展示以下能力：

- 将开放式 Agent 任务建模为可控的序贯决策过程；
- 对 Token、费用、检索次数和延迟进行显式管理；
- 设计可解释、可回放的 Agent 状态与决策机制；
- 构建证据链、引用验证和不确定性表达；
- 使用基线、评测集和消融实验验证系统改进；
- 完成具备可运行性、可观测性和工程质量的端到端系统。

项目不以复制 GPT Researcher 的全部功能为目标。GPT Researcher 被视为参考实现和强基线，本项目重点研究有限预算下的资源分配与停止决策。

## 2. 要解决的具体任务

### 2.1 输入

- 一个需要多来源资料综合的技术调研问题；
- 一组研究预算，例如：
  - 最大 Token 数；
  - 最大模型调用费用；
  - 最大搜索或页面读取次数；
  - 最大运行时间。

示例：

```text
研究问题：
对比 LangGraph、AutoGen 和 CrewAI 的架构设计、适用场景与主要限制，
并为中型企业的内部 Agent 平台给出选型建议。

预算：
- 最大 Token：50,000
- 最大搜索次数：15
- 最大运行时间：5 分钟
```

### 2.2 输出

- 一份结构化 Markdown 研究报告；
- 重要事实和结论对应的来源引用；
- 子问题及其证据覆盖情况；
- 实际消耗的 Token、费用、搜索次数和时间；
- Agent 的行动轨迹与决策原因；
- 对证据不足、来源冲突或仍不确定结论的明确标记。

### 2.3 核心优化目标

在给定预算约束下，尽可能提高最终研究报告的质量和可验证性。

项目关注的不是单纯降低成本，也不是不受约束地追求最高报告质量，而是研究质量、成本和延迟之间的权衡：

```text
maximize    ReportQuality + CitationReliability
subject to  TokenCost <= TokenBudget
            SearchCount <= SearchBudget
            ElapsedTime <= TimeBudget
```

## 3. 核心问题

固定深度的 Research Agent 通常会对每个子问题执行相同数量的搜索和阅读。这会产生两类浪费：

- 简单或证据已经充分的子问题仍被继续研究；
- 困难、存在冲突或证据不足的子问题没有获得额外预算。

本项目的核心问题是：

> Agent 如何根据当前证据状态和剩余预算，动态选择下一步行动，并在继续研究的边际收益不足时停止？

不确定性、证据覆盖度、来源冲突和信息新增率是决策信号；动态检索、补充证据、上下文压缩和停止是策略动作。它们共同服务于预算分配这一核心问题，而不是相互独立的功能堆叠。

## 4. V1 最小闭环

```text
研究问题 + 预算
        ↓
问题拆解 Planner
        ↓
搜索与页面获取 Retriever
        ↓
证据抽取 Evidence Extractor
        ↓
证据状态评估 State Evaluator
        ↓
预算决策 Budget Controller
   ├── 继续：选择下一研究动作
   └── 停止：进入报告生成
        ↓
带引用的报告 Report Generator
        ↓
成本、质量与轨迹记录 Evaluator / Tracer
```

V1 可以使用单 Agent 工作流或状态机实现。模块名称代表职责，不要求每个模块都包装成一个独立 LLM Agent。

## 5. V1 功能范围

### 5.1 必须实现

- 接收技术调研问题和预算配置；
- 将问题拆分为可研究的子问题；
- 搜索公开网页并提取正文；
- 从资料中抽取结构化 claim、evidence 和 citation；
- 维护子问题覆盖度、证据新增率、来源及剩余预算；
- 基于显式规则动态决定继续检索或停止；
- 生成带引用的 Markdown 报告；
- 保存完整运行轨迹和决策原因；
- 统计 Token、费用、搜索次数和端到端延迟；
- 实现固定检索深度的 baseline；
- 在统一任务集上比较 baseline 与预算策略。

### 5.2 V1 暂不实现

- 多用户账号、权限和复杂前端；
- 七八个角色组成的大型多 Agent 团队；
- 强化学习或在线训练策略；
- PDF、Word、图片和视频等多模态研究；
- 企业私有知识库和复杂数据源连接；
- 医疗、法律和投资等高风险领域研究；
- Kubernetes、微服务集群等非必要基础设施。

这些功能只有在能够增强核心论点或提供明确求职展示价值时，才进入后续版本。

## 6. 初始策略设想

### 6.1 研究状态

V1 预计维护以下状态：

```text
ResearchState
- original_question
- subquestions
- evidence_by_subquestion
- supported_claims
- conflicting_claims
- coverage_by_subquestion
- recent_evidence_novelty
- source_diversity
- remaining_token_budget
- remaining_search_budget
- remaining_time_budget
- action_history
```

具体字段和计算方法将在架构设计阶段确定。

### 6.2 候选动作

- `SEARCH_NEW_QUERY`：围绕证据缺口发起新搜索；
- `DEEPEN_SUBQUESTION`：继续研究某个低覆盖子问题；
- `RESOLVE_CONFLICT`：针对相互矛盾的证据进行定向补证；
- `COMPRESS_CONTEXT`：压缩或筛选已有上下文；
- `WRITE_REPORT`：进入报告生成；
- `STOP`：因预算或边际收益原因停止研究。

V1 不要求所有动作一次实现。最低可用策略只需支持“选择待研究子问题、继续检索、停止”三类决策。

### 6.3 停止信号

初始候选信号包括：

- 预算即将耗尽；
- 关键子问题达到最低证据覆盖要求；
- 连续若干轮新增证据率低于阈值；
- 新来源与已有内容高度重复；
- 下一步预计收益低于预计成本。

V1 采用可解释的规则策略；学习型策略属于后续研究方向。

## 7. 基线与实验

### 7.1 最小基线

固定深度策略：

- 固定子问题数量；
- 每个子问题使用固定搜索次数；
- 每次读取固定数量的结果；
- 达到固定轮数后生成报告。

基线与 Budgeted Agent 应尽量使用相同的模型、搜索服务、提示词组件和最大资源上限，避免不公平比较。

V1 的具体固定参数、结构化证据协议和验收要求见 [Fixed-depth Baseline 设计](./fixed-depth-baseline.md)。

### 7.2 初始评测任务

V1 计划构建 30 至 50 个技术调研问题，覆盖：

- 技术框架比较；
- 开源项目调研；
- 工程方案选型；
- 技术发展现状；
- 存在来源冲突或时效性的技术问题。

任务集的具体规模可根据标注和运行成本调整，但必须保证所有策略运行在相同任务上。

### 7.3 核心指标

- 报告事实正确性；
- 关键问题或 claim 覆盖率；
- 引用正确率；
- 引用完整率；
- 来源多样性；
- Token 与实际费用；
- 搜索和页面读取次数；
- 端到端延迟；
- 预算超限率。

最终重点展示质量—成本和质量—延迟的 Pareto 关系，而不是只报告一个缺乏解释的综合分数。

## 8. 可观测性要求

每次运行应至少记录：

- 当前轮次和剩余预算；
- 候选子问题及其覆盖状态；
- 被选择的下一步动作；
- 选择该动作的可读原因；
- 新增证据和被拒绝的资料；
- 每次模型调用的 Token、费用和延迟；
- 触发停止的具体条件。

示例：

```text
Round 3
Action: DEEPEN_SUBQUESTION
Target: 企业部署成本
Reason: coverage=0.42，且目前只有单一来源支持
Cost: 2,810 tokens
Remaining: 16,760 tokens
```

运行轨迹既用于调试和评测，也是简历展示与面试讲解的重要组成部分。

## 9. V1 完成标准

满足以下条件时，V1 可以作为简历项目发布：

- 能够端到端完成至少一类技术调研任务；
- 预算约束在正常运行中能够被执行，而不仅是配置项；
- Agent 至少能根据证据状态作出一次动态研究或停止决策；
- 报告中的主要结论能够追溯到具体来源；
- 每次运行能够输出完整成本和决策轨迹；
- 固定深度 baseline 与预算策略能够在同一任务集上复现；
- README 包含架构图、运行示例、实验结果和已知限制；
- 至少有一组真实、可解释的质量—成本对照结果；
- 核心模块具有基本自动化测试。

## 10. 简历叙事

项目最终应支持如下技术叙事：

> 观察到固定深度的 Research Agent 会对不同难度的子问题平均消耗资源，因此将长程研究建模为受预算约束的序贯决策过程。系统根据证据覆盖度、来源冲突、信息新增率和剩余预算动态调整研究深度与停止时机，并通过统一任务集和固定策略基线评估报告质量、引用可靠性、Token 成本与延迟之间的权衡。

简历中的具体数字必须来自真实实验，在完成评测之前不预设改进百分比。

## 11. 当前已确定与待讨论事项

### 已确定

- 项目名称：Budgeted Research Agent；
- 项目用途：面向大模型应用算法、Agent 开发和 LLM 应用工程岗位的简历项目；
- V1 场景：基于公开网页的技术调研；
- 核心差异：有限预算下的动态研究资源分配与停止；
- 最低交付：报告、引用、决策轨迹、成本统计、基线和评测结果；
- 默认 LLM 接入：Moonshot/Kimi OpenAI-compatible API；
- 搜索与 LLM 解耦，不使用模型内置联网搜索作为核心研究来源；
- 核心编排：自研显式异步状态循环，V1 不依赖 LangGraph；
- 交付形态：Agent Core + CLI + FastAPI + React 可视化控制台；
- 开发顺序：Core/离线测试 → CLI/真实服务 → API/持久化 → Web UI → Adaptive Policy/评测。

### 待讨论

- Kimi 的具体模型，以及 Planner、Extractor、Writer 是否分级使用模型；
- 首个 SearchProvider 的最终选择，当前优先考虑 Tavily；
- 预算的主约束选择：Token、费用、搜索次数或多约束组合；
- 证据、claim 和子问题覆盖度的数据结构；
- 覆盖度和信息新增率的具体计算方式；
- Budget Controller 的第一版规则；
- 引用正确性与报告质量的评测方法；
- 测试任务集的来源与标注方式；
- 是否在 V1 完成后提供 LangGraph Adapter。

## 12. 下一步

在开始编码前，依次完成：

1. 确定一个最小固定深度 baseline；
2. 定义统一的 ResearchState 和证据数据结构；
3. 确定 Budget Controller V1 的输入、动作和停止规则；
4. 编写最小评测协议和 5 至 10 个开发期样例任务；
5. 根据 [技术栈与交付架构](./technical-stack.md) 搭建代码骨架。
